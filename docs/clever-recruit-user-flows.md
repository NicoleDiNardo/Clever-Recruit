# Clever Recruit — User Flows

23 flows per the brief, each specified with: goal, starting state, preconditions, steps, system feedback, decision points, alternative paths, validation, error handling, success state, and candidate analytics events that could be tracked (illustrative — no analytics are implemented; this is a spec for what a real deployment would instrument). Status: **[New scope]** unless marked **[Implemented, extended]**.

---

### 1. Recruiter creates a job [Implemented, extended]
Goal: get a new role into the system. Start: Jobs list. Preconditions: authenticated recruiter/admin. Steps: click "New job" → fill title, company, location, type, salary, description → save as draft. Feedback: inline validation as fields blur; save button shows loading state. Decision point: save as draft vs. discard. Alternative: cancel with unsaved-changes confirmation. Validation: title and company required; salary format checked if entered. Error handling: save failure shows retry, preserves entered data. Success: job created in `draft` status, redirected to job detail (draft view). Analytics: `job_draft_created`.

### 2. Recruiter edits a job [Implemented, extended]
Goal: update role details. Start: job detail. Preconditions: recruiter/admin owns or has access to the job. Steps: click Edit → change fields → save. Feedback: inline validation, save loading state, success toast. Decision: edit while published (changes apply immediately) vs. while draft. Alternative: discard changes. Validation: same as creation. Error: save failure with retry, no data loss. Success: updated job detail shown. Analytics: `job_edited`.

### 3. Recruiter previews and publishes a job [New scope]
Goal: confirm a role reads correctly before it's public, then make it live. Start: draft job detail. Preconditions: draft job with required fields complete. Steps: click Preview → view exactly what a candidate would see (rendered in the public job-detail layout) → return to edit, or Publish. Feedback: preview clearly labelled "Preview — not yet published"; publish button shows loading, then success toast + status badge changes to Published. Decision: publish now vs. keep editing. Alternative: close preview without publishing. Validation: publish blocked if required fields are missing, with a clear list of what's missing. Error: publish failure keeps job in draft, shows retry. Success: job appears on public `/jobs`. Analytics: `job_previewed`, `job_published`.

### 4. Candidate discovers a job [New scope]
Goal: find a role worth applying to. Start: public `/jobs`. Preconditions: none. Steps: browse or filter (location/type) or search by keyword → scan list. Feedback: result count updates live; loading skeleton while fetching. Decision: refine filters vs. open a result. Alternative: no results → empty/no-results state with a "clear filters" action. Validation: n/a. Error: fetch failure → retry state. Success: candidate opens a job. Analytics: `jobs_viewed`, `jobs_filtered`, `jobs_searched`.

### 5. Candidate views a job [New scope]
Goal: decide whether to apply. Start: `/jobs/:jobId`. Preconditions: job exists. Steps: read description, requirements, location/salary → decide. Feedback: none needed beyond page load. Decision: apply vs. leave. Alternative: job closed/unpublished since the link was shared → clear "no longer accepting applications" state, not a 404. Validation: n/a. Error: job not found → distinct not-found state with a link back to the directory. Success: candidate proceeds to apply. Analytics: `job_detail_viewed`.

### 6. Candidate applies [New scope]
Goal: submit an application. Start: job detail → Apply. Preconditions: job is open/published. Steps: fill name, email, phone, upload CV, optional note → submit. Feedback: inline field validation; submit button loading state; disabled while submitting to prevent double-submit. Decision: submit vs. cancel. Alternative: candidate has already applied to this job (see flow 20 territory) — detected by email match, shown as "You've already applied to this role" with a link to check status, not a silent duplicate. Validation: required name/email/CV; valid email format; valid phone format if provided. Error handling: submit failure (network/timeout) keeps form data intact, shows retry. Success: redirected to confirmation. Analytics: `application_started`, `application_submitted`, `application_failed`.

### 7. Candidate uploads a CV [New scope]
Goal: attach a CV to the application. Start: within the application form. Preconditions: application form open. Steps: select or drag a file → see filename/size confirmation → optionally replace. Feedback: upload progress if large; success checkmark; error message inline, not blocking the rest of the form. Decision: keep vs. replace file. Alternative: no CV available — form still submits if CV isn't strictly required for this job (an **[Assumption]**: CV required by default, but this is a job-level toggle a recruiter could set — flagged as Future scope refinement, not built now; default behaviour is CV required). Validation: accepted types (PDF/DOC/DOCX), max size (e.g. 5MB). Error handling: unsupported type → specific message naming accepted types; too large → specific message with the limit; upload failure → retry without losing other form fields. Success: file attached, form remains editable. Analytics: `cv_upload_attempted`, `cv_upload_succeeded`, `cv_upload_failed`.

### 8. Candidate receives application confirmation [New scope]
Goal: know the application went through and what happens next. Start: redirected post-submit. Preconditions: successful submission. Steps: read confirmation, note the status-check path. Feedback: clear success state (not just a toast — a full confirmation page, since this is the moment of highest candidate anxiety). Decision: browse more jobs vs. leave. Alternative: n/a. Validation: n/a. Error: n/a (this page only renders after a verified success). Success: candidate understands next steps. Analytics: `application_confirmation_viewed`.

### 9. Candidate checks application status [New scope]
Goal: find out where they stand without contacting anyone. Start: `/status`. Preconditions: has application reference + email (given at confirmation). Steps: enter email + reference → view status. Feedback: loading state; plain-language status, not internal jargon. Decision: n/a. Alternative: wrong combination → generic "we couldn't find a matching application" (doesn't confirm/deny an email is in the system). Validation: both fields required. Error: lookup failure → retry state. Success: status shown. Analytics: `status_lookup_attempted`, `status_lookup_succeeded`.

### 10. Recruiter searches and filters candidates [Implemented]
Goal: narrow a large candidate list to the relevant subset. Start: `/candidates`. Preconditions: authenticated. Steps: type in search, apply status/stage/role filters, toggle "my candidates only." Feedback: result count updates live; page resets to 1 on filter change (existing fix — previously didn't). Decision: which filters to combine. Alternative: no matches → no-results state distinct from the true empty state (zero candidates at all). Validation: n/a. Error: n/a (client-side filter of already-loaded data). Success: relevant subset shown. Analytics: n/a (internal tool — optional instrumentation only).

### 11. Recruiter reviews a candidate [Implemented]
Goal: assess a candidate for a role. Start: candidates table → row click. Preconditions: candidate exists. Steps: open detail drawer → read profile, assignments, notes, tasks → optionally add a note. Feedback: drawer opens with focus moved in; prev/next keyboard navigation through the filtered list. Decision: move stage vs. just note vs. close. Alternative: n/a. Validation: note requires content before save. Error: save failure → retry, entered text preserved. Success: reviewed, optionally annotated. Analytics: n/a.

### 12. Recruiter moves a candidate through pipeline stages [Implemented (dropdown) → New scope (board)]
Goal: reflect real progress. Start: candidate drawer (today) or pipeline board (new). Preconditions: candidate has an assignment to a job. Steps: select new stage (drawer) or drag/keyboard-move a card (board). Feedback: immediate visual update + toast; board column counts update. Decision: which stage. Alternative: accidental move — undo affordance on the toast for a few seconds (prevents the "accidental rejection" edge case from becoming permanent without a moment to catch it). Validation: can't skip directly to "hired" without passing through required stages — **[Assumption, may be relaxed]**; flagged for confirmation, default behaviour allows any stage-to-stage move since real hiring isn't always linear. Error: move failure reverts the UI optimistically-updated state and shows an error. Success: stage updated everywhere it's shown (drawer, board, table, dashboard counts). Analytics: `candidate_stage_changed`.

### 13. Recruiter shortlists a candidate [New scope]
Goal: flag a strong candidate for hiring-manager attention. Start: candidate drawer or pipeline board. Preconditions: candidate has an active assignment. Steps: click Shortlist → optional note to hiring manager → confirm. Feedback: badge/status update, toast, appears in hiring manager's queue. Decision: with or without a note. Alternative: undo shortly after. Validation: n/a. Error: action failure → retry. Success: candidate marked shortlisted, hiring manager notified (in-product, simulated). Analytics: `candidate_shortlisted`.

### 14. Recruiter rejects a candidate respectfully [New scope]
Goal: close out a candidate who isn't progressing, without it feeling careless. Start: candidate drawer or board. Preconditions: active assignment. Steps: click Reject → **confirmation dialog** (destructive action) → optional reason (internal) → confirm. Feedback: confirmation required before it takes effect (prevents the "accidental rejection" edge case); toast with undo window; candidate's status page updates to a respectful, non-jargon message (e.g. "We've decided not to move forward with your application at this time," never a raw internal stage word). Decision: confirm vs. cancel. Alternative: undo within the toast window. Validation: n/a (reason optional). Error: action failure → retry. Success: candidate rejected, status-page-visible language is respectful. Analytics: `candidate_rejected`.

### 15. Recruiter schedules an interview [New scope]
Goal: set up an interview and have it tracked. Start: candidate detail → Schedule interview. Preconditions: candidate has an active assignment. Steps: choose interviewer(s), date/time, type (call/onsite/video), notes → save. Feedback: conflict check runs before save; time-zone shown explicitly if interviewer/candidate differ. Decision: proceed despite a soft conflict warning, or pick another time. Alternative: interviewer double-booked → blocking or warning state (an **[Assumption]**: warning, not a hard block, since real scheduling sometimes needs overlap — flagged for confirmation). Validation: date/time required, must be in the future. Error: save failure → retry, form data preserved. Success: interview created, appears on Calendar and candidate detail; candidate notified (simulated). Analytics: `interview_scheduled`.

### 16. Hiring manager reviews a candidate [New scope]
Goal: assess a candidate for the hiring manager's own role. Start: hiring manager dashboard or pipeline (scoped). Preconditions: hiring manager assigned to the job. Steps: open candidate (read-only profile + CV) → read recruiter notes if shared → decide. Feedback: same drawer pattern as recruiter, with recruiter-only fields (e.g. compensation notes) hidden per permission rules — **[Assumption: some note types may be recruiter-internal]**, flagged as a design decision to confirm, default: all notes visible to keep it simple for v1. Decision: shortlist, reject, or leave feedback without deciding yet. Alternative: n/a. Validation: n/a. Error: n/a (read path). Success: informed decision made. Analytics: n/a.

### 17. Hiring manager leaves feedback [New scope]
Goal: give the recruiter a structured signal, not just a hallway comment. Start: candidate detail (hiring manager view). Preconditions: as above. Steps: open Feedback → structured fields (recommendation: yes/no/maybe + comment) → submit. Feedback: submit loading state, success toast, visible immediately to the recruiter. Decision: recommendation level. Alternative: save as draft vs. submit — **[Future scope]**, not built; feedback submits directly for v1. Validation: recommendation required, comment optional but encouraged (not enforced — avoids blocking a quick "yes"/"no"). Error: submit failure → retry, text preserved. Success: feedback attached to the candidate, visible to recruiter. Analytics: `feedback_submitted`.

### 18. Recruiter and hiring manager collaborate [New scope]
Goal: reach a shared decision without leaving the tool. Start: candidate detail, viewed by both roles over time. Preconditions: candidate shared with hiring manager (via shortlist, flow 13). Steps: recruiter shortlists → hiring manager reviews + leaves feedback → recruiter sees feedback and moves stage accordingly, optionally replying via a note. Feedback: an activity/timeline on the candidate showing who did what and when (both notes and feedback interleaved). Decision: recruiter acts on feedback. Alternative: hiring manager doesn't respond in time — no automated escalation built (Future scope), but the recruiter's dashboard can surface "awaiting hiring manager feedback" as a visible queue item. Validation: n/a. Error: n/a. Success: a decision is reached and reflected in the candidate's stage. Analytics: n/a.

### 19. Recruiter bulk-updates candidates [New scope]
Goal: act on many candidates at once (e.g. reject all unqualified applicants after a first pass). Start: pipeline board or candidates table. Preconditions: at least one candidate selected. Steps: select multiple (checkboxes or multi-select on board column) → choose bulk action (stage change / reject) → confirm. Feedback: selection count shown; confirmation dialog states exactly how many records will be affected. Decision: confirm vs. cancel. Alternative: **selection becomes empty by the time of confirm** (e.g. a filter changed) → action is disabled with a clear reason, not silently a no-op — this is a named edge case in the brief. Validation: at least one record selected to enable the action. Error handling: **partial failure** — if 8 of 10 updates succeed, the result explicitly reports "8 updated, 2 failed" with a retry option for the failed ones, never a silent partial success. Success: all selected records updated, confirmed by toast with the exact count. Analytics: `bulk_action_performed`.

### 20. Candidate withdraws an application [New scope]
Goal: pull out of consideration. Start: status page. Preconditions: application not already closed (hired/rejected/withdrawn). Steps: click Withdraw → confirmation dialog (destructive, but candidate-initiated) → confirm. Feedback: confirmation required; status updates immediately; recruiter sees it on their side too. Decision: confirm vs. cancel. Alternative: n/a. Validation: n/a. Error: action failure → retry. Success: application marked withdrawn on both candidate and recruiter sides. Analytics: `application_withdrawn`.

### 21. Administrator invites a team member [New scope]
Goal: add a new person to the org with the right access level. Start: `/admin/users` → Invite. Preconditions: admin role. Steps: enter email, choose role (recruiter/hiring manager/admin) → send invite. Feedback: inline email-format validation; loading state; success confirmation that's explicit about simulation ("Invitation ready — would be emailed to X in a live environment," per the product-definition assumption that no real email sends). Decision: which role to assign. Alternative: email already invited/exists → clear duplicate message, not a generic error. Validation: valid email required, role required. Error: submit failure → retry. Success: user appears in the list with a "Pending" status. Analytics: `user_invited`.

### 22. Administrator changes permissions [New scope]
Goal: correct someone's access level. Start: `/admin/users` → select a user. Preconditions: admin role; target user exists and isn't the last remaining admin (prevents an org locking itself out — a real edge case worth designing for). Steps: change role dropdown → confirm. Feedback: confirmation dialog for a downgrade (destructive-ish — losing access is disruptive) or an upgrade; immediate list update. Decision: confirm vs. cancel. Alternative: attempting to demote the sole admin → blocked with an explanation, not a silent failure. Validation: n/a beyond the sole-admin guard. Error: save failure → retry. Success: role updated, reflected immediately in that user's nav on their next action. Analytics: `user_role_changed`.

### 23. User handles a failed action or network error [New scope, cross-cutting]
Goal: recover from a failure without losing work or being confused. Start: any form submission or data-mutating action. Preconditions: n/a — this is a cross-cutting pattern, not a single screen. Steps: action fails (network timeout, server error, validation rejected server-side) → error state renders in place → user retries or edits and resubmits. Feedback: specific, human error copy (never a raw error code alone); entered data is never cleared by a failure. Decision: retry vs. abandon. Alternative: repeated failure (e.g. offline) → an offline/connectivity-specific message distinct from a one-off server error. Validation: n/a. Error handling: this flow *is* the error-handling spec — every mutating flow above (3, 6, 7, 9, 12–17, 19–22) references back to this pattern rather than redefining it. Success: user either recovers and completes the action, or leaves with a clear understanding of what happened and no lost input. Analytics: `action_failed` (with a `reason` property: network / validation / server).
